# 需求规格（001）

来源：对 `testcrewaiflowsfullstack`（下称「源项目」）的**对等重建 + 已知缺陷修复**。
重建目标是同一套业务能力，但按 SDD/TDD 规范落地，并修掉源项目自认的已知问题。

编号规则：`REQ-xxx` 为功能需求，`NFR-xxx` 为非功能需求。编号一经分配不再复用。

---

## 1. 背景与目标

一份完整营销方案要经过「市场调研 → 竞品分析 → 战略制定 → 活动创意 → 文案撰写」多个环节。
传统上需要市场分析师、营销战略师、文案多人协作数天。本系统用**多智能体编排**把这条链路自动化：

> 一次 HTTP 提交 → 异步跑完整条 Flow → 产出「调研报告 / 营销战略 / 活动创意 / 广告文案」。

设计目标与验收标准：

| # | 目标 | 验收标准 |
|---|---|---|
| G1 | 全链路自动化 | 一次提交产出四段结果，无需人工介入（`REQ-003` / `REQ-007`） |
| G2 | 服务化 | 两个 HTTP 接口（提交 / 查询）+ OpenAPI 文档（`REQ-001` / `REQ-003`） |
| G3 | 长耗时推理不阻塞调用方 | 提交接口立即返回 `job_id`，执行异步化、可水平扩容（`REQ-002`） |
| G4 | 机器可消费的结构化产出 | 战略 / 创意 / 文案均为受 Schema 约束的 JSON（`REQ-006`） |
| G5 | 过程可观测、故障可定位 | 每个 Task 的产出落库可查（`REQ-005`） |
| G6 | 供应商不绑定 | OpenAI 兼容网关 / OneAPI / 本地 Ollama 改配置即切换（`REQ-008`） |
| G7 | 状态可信 | 失败作业**永不**被误报为成功（`REQ-004`，源项目严重缺陷） |

---

## 2. 角色与使用场景

| 角色 | 场景 |
|---|---|
| 调用方（系统集成） | 提交调研任务，轮询拿结果，把结构化 JSON 喂给下游系统 |
| 市场运营（前端用户） | 在控制台填表提交、看进度、查历史作业、看每一步产出 |
| 运维 / 排障者 | 通过事件流水与日志定位「哪个 Agent 在哪一步跑偏」 |

## 3. 功能需求

### REQ-001 提交作业

调用方 `POST /api/crew`，携带 `customer_domain` 与 `project_description`，服务**立即**（不等待推理）返回 `job_id`。

- 服务端生成 `job_id`（UUID4），把作业以 `PENDING` 状态持久化，再投递到任务队列。
- 校验失败返回 `422`；队列不可用返回 `503`（不得假装成功）。
- 响应 `202 Accepted` + `{"job_id": "..."}`。

### REQ-002 异步执行

作业由**独立 Worker 进程**执行，与 HTTP 进程解耦。

- 提交接口响应时间与推理耗时无关（`< 200ms`，不含网络）。
- Worker 可多副本水平扩容；队列消息在 Worker 崩溃后可被重新投递（`acks_late`）。

### REQ-003 查询作业

`GET /api/crew/{job_id}` 返回作业的 `status`、`result`、`events`。

- 未知 `job_id` → `404`。
- `result` 在终态前为 `null`；`COMPLETE` 时是结构化结果对象；`ERROR` 时是错误摘要。
- `events` 按时间**正序**返回（最早在前），每条含 `timestamp`（ISO-8601）与 `data`。

### REQ-004 作业状态机（**源项目严重缺陷的修复**）

状态取值：`PENDING → RUNNING → COMPLETE | ERROR`。

- **终态不可变**：一旦进入 `COMPLETE` 或 `ERROR`，任何后续写入都必须被拒绝（拒绝即报错/记日志，**绝不静默覆盖**）。
- **失败优先**：执行过程中抛异常时，作业必须进入 `ERROR` 并携带错误摘要；后续的成功分支**不得**再写入 `COMPLETE`。
- 源项目缺陷：异常分支写了 `ERROR`，随后的成功分支**无条件**又写 `COMPLETE`（此时结果为 `None`），导致失败作业对外显示为完成。本需求即针对该缺陷。
- 源项目用单一 `STARTED` 状态，无法区分「已入队」与「执行中」；本系统拆为 `PENDING` / `RUNNING`（**与源项目的刻意差异**）。

### REQ-005 事件流水（过程可观测）

- 每个 Task 完成后，其原始产出写入事件表。
- 每次状态变更（入队、开始、完成、失败）也写一条事件。
- 事件与作业外键关联；作业被删除时事件级联删除。

### REQ-006 结构化输出

三个 Pydantic 模型约束模型输出：`MarketStrategy` / `CampaignIdea` / `Copy`（字段见 `020-contracts-domain.md`）。

- 模型输出**必须**先过 Schema 校验才能进入 `result`；校验失败该作业进入 `ERROR`，不得把裸文本当结构化结果返回。
- 校验失败的错误信息必须包含「哪个模型、哪个字段」以便定位。

### REQ-007 双 Crew 链式编排

Flow 分两阶段，第一阶段产出作为第二阶段的输入上下文：

1. `@start` **市场调研 Crew**：首席市场分析师（检索工具 + 网页抓取）→ 全面调研报告。
2. `@listen` **内容创作 Crew**：首席营销战略师（理解 → 战略 → 创意）、首席创意内容创作师（文案，显式依赖战略与创意两个 Task 的产出）。

- Agent 的 role / goal / backstory 与 Task 描述、期望输出**声明式**放在 YAML 中，新增角色不改流程代码。
- 变量 `{customer_domain}` / `{project_description}` 由 `kickoff(inputs=...)` 统一注入。

### REQ-008 多模型供应商适配

三种适配，配置切换：`openai`（OpenAI 兼容网关，默认）/ `oneapi` / `ollama`（本地）。

- 供应商与凭据只从配置读取（`REQ-009`）。
- 另提供 `fake` 供应商用于离线测试与系统测试的确定性路径（**本系统新增**）。

### REQ-009 配置与凭据安全

- 所有密钥 / 口令 / 连接串只从环境变量读取，**源码与测试中不得出现真实值**。
- 提供 `.env.example`，仅含占位符。
- 配置文件用绝对路径定位，**任意工作目录启动都能读到**。
- Redis 口令含特殊字符（`@ : /`）时自动 URL 编码，无需人工转义。

### REQ-010 输入校验

- `customer_domain`：非空、长度 3–255、去除首尾空白。
- `project_description`：非空、长度 10–4000。
- 校验规则集中在领域层，HTTP 层复用同一套规则（**单一事实来源**）。

### REQ-011 错误语义

- `404` 未知作业；`422` 入参非法；`503` 队列/存储不可用；`500` 未预期错误。
- 错误体统一为 `{"detail": "..."}`（兼容 FastAPI 默认形状，前端已按此解析）。
- 未预期错误**不得**把堆栈或连接串泄露给调用方。

### REQ-012 前端控制台

Vue 3 + TypeScript + Vite 单页控制台：

- 提交作业表单（两个字段 + 校验提示 + 提交中禁用）。
- 提交后**立即**拉取一次状态，之后每 3 秒一次；到达终态（`COMPLETE` / `ERROR`）**自动停止轮询**。
- **停止轮询的完整规则**（源项目的痛点之一是「作业结束后仍在轮询，浪费请求」）：
  | 情况 | 行为 |
  |---|---|
  | `COMPLETE` / `ERROR` | **停止**——已到终态，不会再变（`REQ-004`） |
  | `404` 作业不存在 | **停止**并提示——重试不会让不存在的作业出现，继续轮询只是白刷 |
  | `503` 等暂时性错误 | **不停止**，显示错误，下个周期继续重试 |
  | 未知状态（未来新增） | **不停止**——契约规定新增状态不算破坏性变更（`CT-002`），前端必须容错 |
- 按 `job_id` 查询历史作业（刷新页面不丢：`job_id` 反映到 URL query，可分享/回填）。
- 事件流水展示（时间 + 内容），四态状态徽章（运行中带呼吸动效），适配深色模式。
- 开发环境通过 Vite proxy 转发 `/api` 到后端，避免跨域配置差异。

### REQ-013 可观测性

- 结构化日志：作业 ID、阶段、事件。
- 可选开启 CrewAI Traces（配置开关），用于下钻 Agent 决策、工具调用参数、Token 消耗。

### REQ-014 健康检查

`GET /healthz` 返回 `200 {"status":"ok","version":"..."}`，只反映进程存活、不探测下游依赖。
供 CI 与系统测试等待服务就绪使用（`022` CT-003）。

## 4. 非功能需求

| 编号 | 需求 | 验收方式 |
|---|---|---|
| NFR-001 | 单元 + 契约 + 集成测试**可完全离线**运行（无网络、无真实模型） | CI 在断网/无密钥环境下 `make test` 全绿 |

## 5. 明确不做（Non-Goals）

避免范围蔓延，以下**本期不做**，如需再做要新开 REQ：

| 不做 | 原因 |
|---|---|
| 用户体系 / 鉴权 / 限流 | 源项目也没有；属独立课题 |
| 作业取消 / 断点续跑 | 需要 Flow 状态持久化，成本高，另立需求 |
| 多租户配额与计费 | 同上 |
| 结果去重 / 缓存 | 需要业务侧定义「相同输入」语义 |
| 移动端适配 | 前端只保证桌面与窄屏可用，不做原生 App |

## 6. 与源项目的差异清单（刻意为之）

| # | 差异 | 理由 |
|---|---|---|
| 1 | 状态由 `STARTED` 拆为 `PENDING` / `RUNNING` | `REQ-004`：单一状态无法区分入队与执行中 |
| 2 | 终态不可变，且有测试守护 | `REQ-004`：源项目「失败误报成功」严重缺陷 |
| 3 | 端口抽象 + 依赖倒置 | `NFR-001/004`：源项目模块级直连 MySQL/Celery，无法离线测试 |
| 4 | 新增 `fake` LLM 供应商 | `NFR-001`：让系统测试可确定性、可离线 |
| 5 | 全套自动化测试（源项目 `tests/` 为空目录） | 本项目的立项理由本身 |
| 6 | 结构化输出加 Schema 校验与失败即 `ERROR` | `REQ-006`：源项目把校验交给框架，失败时语义不明 |
| 7 | 启动不再要求「必须在源码目录下」 | `NFR-006`：源项目已知问题 |
| 8 | `result` 由自由文本改为结构化 JSON 对象 | `REQ-006`：源项目结果是 `str()` 后的文本，下游无法解析 |
| 9 | 字段重命名 `tatics`→`tactics`、`KPIs`→`kpis` | 源项目拼写错误 / 命名不统一；前后端一并重建，不做别名兼容 |
| 10 | CORS 默认不是 `*`，且不与 `allow_credentials` 同用 | `CT-004`：`*` + credentials 是无效且不安全的组合 |
| 11 | 新增 `GET /healthz` | `REQ-014`：源项目无探活接口，CI 与系统测试无法等待就绪 |
